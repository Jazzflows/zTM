# Working Preferences

How the user wants work delivered in this project. These are standing rules; the user's current message overrides any of them when the two conflict.

## Starting and running a chat

- At the start of every chat, work out which skills apply and use them from the first message, so the same skills run across the whole chat (routing table in project-instructions).
- Before delivering anything, self-review it against the relevant marketing skills and docs (copy, offer, psychology, launch, referrals) and iterate until the quality holds. Deliver the revised version, not the first draft.
- When asked for expert advice or expert feedback, run the marketing-council skill with the 12 advisor dossiers (Hormozi, Handley, Dunford, Sharp, Hopkins, Ogilvy, Schwartz, Halbert, Vaynerchuk, Sutherland, Brunson, Godin).
- When the user supplies a structure, dates or a referral program, build on what they gave rather than older records, unless they ask for the earlier version.

## Shape of the output

- Build the simple thing that was asked for. A sorted list means a sorted list, not a multi-tab system around it.
- Default to prose. Bullets only where the content is a real list.
- Strategy and plan documents state the plan (what Zoth is presented as, what will run), not the rationale, timing or ownership justification, unless asked.
- Prefer a visual (a grid or flow showing how the plan runs and what it lands) over long prose sections.
- Anything for the founder's approval is a visual, never a document.
- Launch checklists and readiness documents bundle activities: a few points per workstream, phased before launch, launch day and after launch, no numbered sub-tasks. For an email sequence: copy written, reviewed, sent on launch day, and nothing more.
- A blockers or "needs to be locked" list holds only genuine open questions someone must answer (budgets, signatures, compliance positions, build dates). Routine production steps sit as sub-tasks under the item they serve.
- In tracker and calendar sheets, every tab carries a tracker at the top, and the blockers section sits below the calendar.
- In spreadsheets, values are calculated by formula, never typed in. Formulas auto-populate and never hardcode row numbers or fixed column ranges. Rates and other inputs live in one cell that everything else references.

## Writing

- Never use em dashes, in any output. This is a standing anti-AI-slop rule.
- Never use relative dates. Always the calendar date.
- Never name owners in written output. Use [OWNER], [FOUNDER] and similar placeholders.
- Writing never reads as unsure. Lead with the claim, state figures plainly, stop stacking caveats. Raise a genuine conflict once, in its own place, then write with conviction.
- Long-form copy uses active voice, short direct sentences and the fluid style of crypto KOL writing (reference: Stacy Muur). No passive constructions, no filler sentences. The audience is institutional and crypto-savvy: depth, not explainer framing.
- Hyperlink facts, figures and studies to their source wherever possible.
- zOPAL's headline yield is 12% base APY; Zocta adds up to 4% more. When reviewing marketing assets, a standalone "12%" is correct and intentional. In social posts, Zocta Points stay on their own line.
- X threads for zVaults run at most 2 posts, ending with a CTA to zOPAL.

## Revisions and reviews

- When the user sends an updated version of work, review it with a reviewer's lens and reply with the critique, rather than acknowledging the update.
- When the user asks "what is this" about a specific line, correct that line and return the full corrected piece.
- When the user asks for a revision to one channel or section, return only that revised part.

## Outreach and BD

- Outreach output is copy-and-send messages, one per named person, with the user's own note on that person visible beside the draft.
- Every named person in outreach lists, guestlists and BD output carries a LinkedIn profile link and, where possible, an email address.
- Next steps are written in the user's own words, not reworded or expanded.
- In BD digest emails, each lead gets a single-sentence update.
- Outgoing emails never describe the state of a CRM record ("no time on file", "no contact made yet"); only the state of the relationship. If a field is empty, say nothing.
- "Update [company] in pipeline" means change the Attio status and next step only.

## Tools

- Zerply is for checking content quality only. Never publish through Zerply or move content into it.
- The master go-live calendar workbook, if touched again: write only in column L ("Claude Access"), only on sub-task rows, finished paste-ready copy only, one tab at a time on the user's instruction.
